# 从源码理解这个 Agent

这份指南描述当前 mini 实现。目标是让一个终端程序能连续接收任务，自主选择工具，对真实代码做有边界的修改，再把执行结果交回模型；不引入 Agent 框架、数据库或多 Agent。

## 1. 一条用户输入如何变成实际操作

入口链路：

    mini-coding-agent / python -m mini_coding_agent
      -> cli.main()
      -> Agent.run(task)
      -> request_model(messages, tools, model, base_url)
      -> assistant.tool_calls
      -> execute_tool(name, arguments_json, workspace_root)
      -> 实际文件操作或命令
      -> role=tool 的结果消息
      -> 下一次 request_model()

模型并没有运行 Python 函数。模型只返回工具名称和 JSON 参数；真正的副作用来自应用里的工具函数。

### 启动前如何取得密钥

`cli.main()` 在创建 Agent 前调用 `config.ensure_api_key()`：先读取已有环境变量，再尝试 Windows 保存项，最后进入 `configure_api_key()` 提示输入。`--help` 会由 argparse 提前退出，不需要配置密钥。

`configure_api_key()` 用 `getpass.getpass()` 隐藏输入；不支持隐藏输入时停止配置，不退回明文输入。密钥不会作为任务加入 messages。交互命令 `/key` 也只在 CLI 中调用这个函数，不经过 Agent 或模型。

取得密钥后写入 `os.environ["DEEPSEEK_API_KEY"]`。这是当前 Python 进程的环境变量，不会给外部 PowerShell 设置永久环境变量。`model_client.request_model()` 每次请求仍通过原来的 `load_api_key()` 读取，因此下一次请求会使用新密钥，无须重建 Agent，也不会清空对话。

如果用户选择保存，`credential_store.save_key()` 通过标准库 `ctypes` 调用 Windows 的 `CredWriteW`；下一次启动由 `load_saved_key()` 调用 `CredReadW` 取回。保存的标识是 `mini-coding-agent/deepseek-api-key`，密钥转为 UTF-8 字节放在 CredentialBlob 中。`_Credential` 描述的是 Windows API 要求的 C 结构，不是聊天消息。读取完成后 `CredFree` 释放系统分配的缓冲区。

只有明确输入 `y` 才持久保存。保存失败仍可用于当前会话；留空或中断输入时保留原密钥。环境变量的优先级高于保存项，所以启动终端里已有的旧密钥也会优先使用。保存项属于当前用户的本机凭据，不属于所有用户共享的机器配置。

配置和端到端测试只使用假密钥与模拟凭据 API，不写入真实 Windows 凭据管理器；SDK 测试检查认证头已经更新，同时检查密钥没有进入聊天消息或程序输出。

## 2. 为什么使用一个 Agent 实例

原来每次调用 run_agent() 都创建新消息列表，适合一次演示，但下一句话无法继续前一轮任务。

现在 CLI 在启动时创建 Agent，交互循环复用这个实例。messages 中保存 system、user、assistant 和 tool；run() 每次追加一个用户任务。模型能继续前面的任务，是因为程序把这些消息再次发送，不是 SDK 自动记忆。

changes 记录本会话完成的文件操作与 Diff，commands 记录真实命令结果；/diff 直接查看这些证据。它们是内存状态，退出不会恢复。/clear 清空状态但不修改磁盘。

上下文过长时只删除最早的完整用户轮次；绝不单独删除一个 tool 回复。当前轮超出上限则停止，避免静默丢掉正在使用的源码或审批信息。

## 3. 为什么工具定义与执行分开

Schema 让模型知道工具名称和参数规则；它不是运行时权限。

程序还会做两层检查：

1. Agent 检查名称是否在本次启用的工具集合里。没有 --allow-edit，就不能调用文件写入；没有 --allow-commands，就不能调用命令。
2. tool_registry 验证 JSON 对象、必填字段、额外字段、类型和基本范围，再调用具体函数。

即使模型请求了隐藏工具，也只会收到失败反馈。参数错了通常交回模型修正，而不是把整个 CLI 关闭；连续失败、请求次数和工具次数都有上限。

原来的计算工具和 run_check 包装器保留给 src/examples 中的学习示例，正式 CLI 使用文件、搜索和通用命令工具。

## 4. 文件编辑为什么有这么几步

read_file 返回内容和原始字节的 SHA-256，同时记录 (工作区, 文件) 对应的读取版本。

edit_file 的顺序：

1. 解析相对路径，拒绝越界、链接和受保护路径。
2. 确认 base_version 来自实际读取，并与当前文件字节一致。
3. old_text 必须唯一匹配，防止随意替换同名语句。
4. 仅规范化替换片段的换行，保留其他内容；构造新字节和 Diff。
5. 展示 Diff，由真正的终端用户批准，模型不能传一个 approved=true 绕过它。
6. 写入同目录临时文件，关闭句柄后再替换。
7. 替换前重读目标并检查哈希，防止等待确认时 IDE 已保存新内容。
8. 替换成功后清除旧读取记录，下一次编辑需要重新读取。

创建文件不要求版本，因为它要求目标不存在，并使用 xb 排他创建。审批期间有人创建同名文件时，创建会失败，不会覆盖。

这些措施降低意外覆盖和半写入风险，但临时替换不是与外部进程之间的严格 compare-and-swap，也不保证完整 Windows ACL 的复制。

## 5. 搜索为何只返回片段

模型通常不知道函数在哪。search_code 负责找位置，read_file 再读取上下文，edit_file 最后应用修改。一次把整个仓库塞给模型既昂贵也会淹没有用信息。

搜索用标准库按目录遍历，先排除依赖、凭据、链接等路径，再用 glob 过滤文件并逐行查找字面量。返回相对路径、从 1 开始的行号和关键字附近的片段。

结果数、文件大小、扫描数量和时间预算限制成本；truncated=True 表示结果不完整。时间预算是遍历检查点上的软预算，不能中断底层阻塞 I/O。

Git 可用且工作区是仓库根目录时，使用只读的 git ls-files 获取可见文件，遵循 Git 忽略规则。工作区只是父仓库中一个被忽略的练习目录时，不继承父仓库规则，防止练习文件全部消失。

## 6. 通用命令如何替代固定验证脚本

run_command 接收 argv 数组、工作区内的 cwd 和时限。模型可以选择现成的测试、构建、语法检查或运行入口，无须用户为 Agent 单独准备脚本。

程序会展示完整命令、目录和时限，审批后执行这份参数。shell=False 表示直接启动可执行程序；如果明确请求 powershell.exe 或 cmd.exe，它们本身仍能执行任意代码，所以用户确认和可信项目边界很重要。

子进程使用精简的环境变量，项目额外需要的变量由 --pass-env 显式加入。stdout/stderr 用两个线程持续消费，保留有限预览，防止管道堵塞；输出超过总预算则停止。

Windows 启动进程时先挂起，加入 Job Object 后恢复初始线程。这样即使虚拟环境 Python 启动另一个解释器，后代也属于 Job。结束、超时或取消时关闭带 KILL_ON_JOB_CLOSE 的 Job 回收所属进程。POSIX 使用独立进程组。

这里最复杂的 ctypes 代码集中在 processes.py，其余逻辑不需要知道 Windows 句柄细节。它管理进程生命周期，不提供文件或网络沙箱；后台服务不是当前支持的使用方式。

## 7. 执行完成、检查通过和任务完成

这三件事不同：

- 工具成功返回：确实取得了执行结果。
- 进程退出码为 0：命令按自己的规则正常退出。
- 满足用户需求：需要结合实际修改、合适的检查和用户要求判断。

因此测试失败仍以工具结果返回，模型可以读取 traceback 并继续修复。没有运行检查就必须说明未验证，不能把自然语言判断冒充测试结果。

用户拒绝后，运行时立即停止新操作，并给当前批次的剩余调用补上 skipped 回复。中断也会封闭所有 tool_call_id，下一轮才不会因协议不完整而被 API 拒绝。

## 8. 如何看测试

先看 test_cli_e2e.py 的两个完整场景：

1. 在一个已有项目中搜索、读取，运行已有 unittest 取得失败，编辑代码，再运行同一检查取得通过，保留用户其他文件和原测试。
2. 从空目录创建多个文件并实际启动应用。

SDK 收到的是内存 HTTP 传输返回的 Chat Completions 响应，避免联网和付费；后续文件写入和 Windows 子进程都真实执行。其他测试单独覆盖冲突、拒绝、只读门禁、工具批次、上下文和超时清理。

测试通过证明程序在这些场景中正确执行了协议与工具，不证明真实模型永远选择正确步骤。模型质量和具体任务仍需要实际使用来评估。
